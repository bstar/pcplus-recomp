# Attached terminal PROGRAM ownership

The experimental capability7 terminal and ASPECT interpreter now execute
DOS/RUN/SHELL while retaining the actual parent renderer. The
[validation ledger](validation/aspect-parent-process.json) records 13 actual DOS
cases and 505 checks, including COM1/COM2 crossed with N/S/H/B flow. All 77
external leases retire. Separate parent/child policy models pass 77 linked
cases, and a blank source tree reproduces 25 products exactly.

Normal capability6 TERMINAL and the 105-slot ASPECT interpreter remain
byte-identical. The separate raw 108-slot diagnostic also remains byte-identical
to its earlier 56-case DOS proof. No normal opcode publication or complete
application gate closes.

## Handoff and view ownership

Capability7 adds scalar PROGRAM_BEGIN and PROGRAM_END operations to the existing
ASIOv4 descriptor. Ordinary capability6 products explicitly reject the newer
version. The actual resident bridge still checks child PSP/DS, allocation,
callback and guarded stack ownership; no child pointer is added to this API.

BEGIN requires an attached child, a live child UART and the parent's admitted
80x25/page0 view. It records SAVE versus NOCLEAR ownership. While held, both
halves reject ordinary rendering, status, key and other requests; the parent
also rejects a second BEGIN or ordinary detach. Child callbacks cannot read or
write the UART through this suspended renderer owner.

The actual VM scope, ASX reader and six numbered streams then use the existing
[private-handle and PROGRAM controller](ASPECT_PROCESS.md). After a real child
returns, UART ownership, private DOS handles and buffered streams restore before
END. END checks the retained parent view and retires ownership even when that
view check fails. Argument, state and reserved bridge failures retain the child's
local owner for a valid END retry; they do not silently permit new rendering.

A retained pre-fix linked counterexample returned STATE10 from END and then
allowed a new EMIT. The corrected child admits retirement only for the parent's
defined completed outcomes: success0, rejected view3 and returned UART14. Its
48 linked policy cases include rejected-END retention and successful retry;
the parent supplies 29 separate acquisition/rejection/retirement cases.

The NOCLEAR geometry-change and raw-exit247 hints reach END. On this deliberately
fixed view, END revalidates real BIOS geometry and the retained renderer rather
than running RIS, clearing the child's text or replacing the profile, keymap,
history and modes with startup defaults. This is maintained fixed-view policy,
not a recovered implementation of the original general geometry/UI service.
Broader views remain required work.

## Actual DOS evidence

Four focused cases check graphics recovery with saved text, visible NOCLEAR
text/attributes, native WAIT consuming an actual queued BIOS key, and NOCLEAR
exit247 refresh. A fifth child deliberately drops DTR: the UART owner correctly
returns LINE, ASPECT reports error14, the renderer lease retires and the normal
parent keyboard and device baseline recover.

Each of the eight full COM/flow cases executes graphics SAVE, text NOCLEAR,
WAIT, exit247, graphics NOCLEAR, a missing command, DOS VER and a real nested
command shell. EXECUTE invokes the actual DOS compiler for a missing NEXT.ASX,
then the new script executes another child and continues. The compiled output
matches the host compiler exactly. There is no substitute successful executor
or parser.

Five input streams retain prefetched bytes and exact positions; a sixth output
stream is flushed before EXEC. The child proves that nonstandard inherited
handles are absent and reads the pending output through its own independently
opened DOS handle. Selected name/entry/password, environment, FGETS setting and
active directory enumeration survive into NEXT. Nonidempotent input tables and
seven-bit receive masks are exercised, followed by an exact post-child CPR and
ordinary parent keyboard output. The child changes UART framing, divisor, IER,
MCR, IRQ vector and the selected PIC bit while preserving DTR in success cases.

A passive INT21 observer forwards the actual DOS calls unchanged. Around each
direct nested EXEC attempt it compares **10,276 exact parent bytes**, including
the selected 496-byte directory context, translation table/mode, settings,
keymap/tabs, renderer metadata and planes, and ASIO descriptor. Failed DOS EXEC
attempts remain distinct from successfully launched children; the missing target
exercises multiple PATH attempts. The observer records lease acquisition and
retirement counters, and the suite separately compares parent JFT/file owners,
final hardware snapshots, child markers and continued renderer/serial behavior.
It neither supplies input/replies nor repairs state.

These tests use DOSBox's BIOS/UART at 38400 baud and synthetic files/directory
records. They do not establish physical CTS/DCD timing or loaded-input retention
during arbitrary external programs. In particular, NONE flow cannot guarantee
incoming data preservation while a child owns the machine.

## Rebuild and reproduce

Run through the pinned Nix toolchain:

```sh
./tools/build test-aspect-parent-process
./tools/build test-aspect-parent-process-source
```

The separate outputs are `build/terminal-process/TERMINAL.EXE` and
`build/aspect-process-parent/ASPECT.EXE`. They are not installed onto the DOS
drive. New test labels preserve earlier evidence. The source proof starts with
declared source files only, without original executables, old objects or REA
databases, and reproduces both normal programs, both experimental programs, the
DOS compiler and 20 process/display/serial products.

Retained failures include a fixture that dropped DTR, a directory override that
selected the wrong emulated COM port, and an incorrect 20-versus-21-character
saved-screen expectation. Their captures are not counted as accepted cases.

## Remaining publication requirements

Complete nonlocal-fault cleanup during external ownership before enabling the
three slots in the normal interpreter. Bind the original macro keyboard,
mouse/window and error-notice services and broader views. Repeat application
workflows and transfers/doors against the current owned ENiGMA and Synchronet
services, then validate loaded input, actual DOS kernels and physical RS-232
Wi-Fi modem/hardware behavior. This checkpoint does not resolve the separate
live ENiGMA keyboard-decoder failure.
